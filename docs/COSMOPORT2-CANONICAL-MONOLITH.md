# Cosmoport 2.0 — единая согласованная модель продукта

> **Статус:** master engineering brief / сводный канон для следующего цикла планирования  
> **Дата:** 30 августа 2026  
> **Текущий продуктовый scope:** Cosmoport в зоне разработки (ЗР) одной закрытой airgap-сети  
> **Текущий пример:** ПлЦР — Платформа цифрового рубля  
> **Код пока не меняется:** документ фиксирует проверенные тезисы и целевую модель

---

## 1. Что строим

Cosmoport 2.0 — это операторский **Sovereign Run Control Plane** для управления приложениями, сборками, жизненными циклами, качеством, Evidence и релизными пакетами.

Это не:

- копия легаси-портала один-в-один;
- глобальный межсеточный диспетчер;
- единая админка всех зон;
- собственный DAST-сканер;
- замена PrettyK;
- портал, в котором все зоны живут в одной БД.

Целевая задача текущего инстанса:

```text
создать и организовать приложения
→ связать их в проекты
→ работать с Git
→ запускать сборки и ЖЦ
→ собрать Findings/Evidence
→ пройти внутренние Gate и PrettyK DAST/QG
→ создать релиз
→ сформировать подписанный релизный пакет
→ передать пакет во внешний контур СОД/МЗП
```

## 2. Инстансная архитектура: одна копия на одну зону одной сети

### 2.1. Правильная топология

Cosmoport поставляется как отдельная копия для конкретного изолированного контура:

```text
Airgap-сеть / кластер ПлЦР
├── Cosmoport ЗР
│   ├── PostgreSQL ЗР
│   ├── Gitea ЗР
│   ├── PrettyK / DAST runner ЗР
│   └── Cosmoport Control Station ЗР
├── Cosmoport ЗТ       (позже, отдельная копия)
└── Cosmoport ЗПЭ      (позже, отдельная копия)
```

Зоны могут находиться:

- на разных хостах;
- в разных airgap-сетях;
- с разными Gitea;
- с разными БД;
- с разными настройками ЖЦ;
- с разными экземплярами PrettyK.

Не существует единого межзонового Cosmoport, который напрямую управляет всеми зонами.

### 2.2. Текущий scope

Сейчас строится:

```text
Cosmoport instance = ПлЦР / ЗР
```

ПлЦР не хардкодится. Все значения являются конфигурацией инстанса:

```text
COSMO_INSTANCE_ID
COSMO_NETWORK_ID
COSMO_PLATFORM_LABEL
COSMO_ZONE=zr
COSMO_FORGE_URL
COSMO_PRETTYK_URL
```

Тот же продукт позднее можно поставить в другой закрытой сети, передав другую конфигурацию.

### 2.3. Domain

Текущая идея `Domain` как жёсткого tenant boundary признана неверной.

В целевой модели нет бизнес-сценария:

```text
один Cosmoport → несколько изолированных доменов → общий трансфер между зонами
```

Вместо этого:

```text
Instance Config = контекст конкретной поставки
КИТС = тег приложения
Project = контейнер приложения/связей/релизной работы
```

Старую сущность `Domain` не надо использовать как:

- обязательный контекст каждого запроса;
- замену КИТС;
- замену airgap-сети;
- замену зоны;
- замену Gitea;
- tenant boundary.

Текущий `X-Cosmo-Domain` и жёсткий `require_domain()` считаются переходным легаси-следом и требуют отдельной миграции. Обычные GET-запросы не должны падать только потому, что пользователь не выбрал фильтр.

## 3. КИТС — тег карточки приложения

### 3.1. Смысл КИТС

КИТС — это не домен и не зона. Это тег, которым помечают приложения для:

- сортировки;
- фильтрации;
- организационной принадлежности;
- автоматической видимости Администратора КИТС;
- агрегации в таблицах проектов.

Одно приложение может иметь несколько КИТС-тегов:

```text
Application ←→ KITS tags
```

КИТС не создаёт:

- отдельную БД;
- отдельный портал;
- отдельный Gitea;
- отдельную airgap-сеть;
- жёсткую изоляцию чтения;
- обязательный `X-Cosmo-Domain`.

### 3.2. Переключатель КИТС

Пользователь может выбрать:

```text
Все доступные КИТС
КИТС-1
КИТС-2
КИТС-3
```

Это UI-фильтр. Он не заменяет серверную авторизацию.

Режим «Все» означает:

```text
показать всё, что пользователь имеет право видеть
```

а не:

```text
передать фиктивный domain_id или выбрать несуществующий cbr
```

## 4. Project — новая главная сущность

### 4.1. Почему нужен Project

В легаси используется категория:

```text
Нулевой уровень
Первый уровень
Второй уровень
Группирующий уровень
```

По скрейпу формы создания приложения видно, что «Группирующий уровень» является специальным уровнем над обычными приложениями. По смыслу он закрывает потребность в контейнере для связанных приложений.

В Cosmoport эта потребность решается не костылем, а отдельной сущностью `Project`.

### 4.2. Уровни приложений и проект

```text
Project
├── Application L2
│   ├── Application L1
│   │   ├── Application L0
│   │   └── Application L0
│   └── Application L1
└── другие приложения проекта
```

Правила:

- L0/L1/L2 — уровень приложения;
- уровень не заменяет проект;
- «Группирующий уровень» не переносится в новую модель;
- любое приложение получает проект;
- даже одиночная L0-карточка создаётся внутри проекта;
- приложение может входить в несколько проектов;
- связи приложений хранятся отдельными рёбрами;
- Project не равен старой Group.

### 4.3. Пустой проект

Проект может существовать без приложений. В таком случае он не является пустой декоративной записью, а хранит метаинформацию:

- название;
- код;
- назначение;
- обоснование создания;
- владелец;
- предполагаемый состав;
- область ответственности;
- статус;
- дату создания;
- планируемые приложения.

### 4.4. Создание приложения

Основной поток:

```text
ИТ-лидер
  → создаёт проект
  → создаёт приложение внутри проекта
  → выбирает уровень L0/L1/L2
  → при необходимости назначает один или несколько КИТС-тегов
  → создаёт или подключает Git-репозиторий
```

Не нужно создавать «карточку-группу» вместо проекта.

Приложение может быть добавлено в существующий проект позднее.

### 4.5. Проект и репозитории

Проект не обязан иметь отдельный Git-репозиторий:

```text
Project
├── Application A → Repository A
├── Application B → Repository B
└── Application C → Repository C
```

В пределах текущего ЗР-инстанса используется Gitea ЗР. Gitea ЗТ и Gitea ЗПЭ будут другими, когда появятся соответствующие копии Cosmoport.

## 5. Команды и видимость

### 5.1. Команды на двух уровнях

```text
Project Team
Application Team
```

При batch-добавлении из проекта:

```text
Project Team
→ базовый состав для приложений проекта
→ индивидуальные Application Team overrides
```

На уровне приложения можно:

- добавить участника;
- исключить участника;
- изменить роль;
- добавить локальное разрешение;
- убрать унаследованное разрешение;
- указать причину override.

Система должна различать:

- участника, пришедшего из команды проекта;
- локально добавленного участника;
- локально исключённого участника;
- локально переопределённую роль.

### 5.2. Администратор ИБ — владелец PrettyK/QG

Администратор ИБ — не обычный участник команды приложения.

Это «бог» security-контура PrettyK:

- сам открывает нужные проекты и приложения;
- имеет глобальную видимость;
- управляет финальным DAST/QG-контролем;
- определяет, можно ли релиз считать готовым к передаче;
- не должен добавляться ИТ-лидером;
- не должен зависеть от ручного включения в Application Team.

Без приемлемого PrettyK DAST/QG-результата:

```text
релизный пакет не считается готовым к перемещению в следующую зону
```

### 5.3. Администратор КИТС

Администратор КИТС не добавляется вручную в каждую карточку.

Если у приложения есть КИТС-тег Администратора КИТС, он автоматически получает доступ к проекту.

Правило видимости внутри такого проекта:

```text
Приложения с его КИТС:
  полноценный доступ по роли

Остальные приложения проекта:
  readonly-превью
  не кликабельны
  только название и app-code
```

Администратор КИТС не становится Администратором ИБ и не получает автоматических полномочий PrettyK.

### 5.4. ИТ-лидер

ИТ-лидер:

- создаёт проекты;
- создаёт приложения;
- выбирает уровни L0/L1/L2;
- назначает КИТС-теги, если это нужно;
- создаёт или подключает репозитории;
- задаёт начальные метаданные.

ИТ-лидер не обязан:

- добавлять Администратора ИБ;
- добавлять Администратора КИТС;
- вручную строить глобальную админскую цепочку.

### 5.5. Руководитель разработки

Руководитель разработки:

- строит связи приложений;
- управляет структурой проекта;
- определяет состав релизов;
- создаёт индивидуальные релизы;
- создаёт общие batch-release проекта;
- задаёт порядок очереди.

### 5.6. Команда приложения

Команда:

- работает с кодом преимущественно в собственном окружении;
- использует Git/Gitea;
- иногда использует Web IDE;
- запускает сборки;
- получает результаты ЖЦ;
- видит приложения, в командах которых участвует.

### 5.7. Эксплуатационные администраторы

Глобальную видимость должны иметь соответствующие эксплуатационные роли:

- Администратор ИБ;
- Администратор НШР;
- `admin_service`;
- обычный системный администратор.

Администрирование опирается на PrettyK, где уже заложены `admin_service` и Администратор НШР. В Cosmoport нужен рабочий локальный RBAC-интерфейс, но не вторая независимая админская вселенная.

### 5.8. Итоговая видимость

```text
Пользователь видит приложение, если:
  он состоит в Application Team
  ИЛИ он входит в Project Team с унаследованным доступом
  ИЛИ он Администратор КИТС соответствующего тега
  ИЛИ он глобальный администратор
```

UI-фильтр КИТС только сужает выдачу и не расширяет права.

## 6. Навигация и операторские поверхности

### 6.1. Основное меню

```text
Обзор
Проекты
Приложения
Пайплайны
Прогоны
Гейты
Релизы
Сборки
Деплои
```

### 6.2. Обзор

Главный дашборд показывает **проекты**, а не плоский миллион приложений.

Таблица проектов:

- проект;
- КИТС-теги;
- число приложений;
- количество L0/L1/L2;
- руководитель разработки;
- статус;
- последний релиз;
- дата обновления;
- действия.

Фильтр КИТС переключает набор проектов, но не является domain boundary.

### 6.3. Проекты

Второй основной пункт после Обзора:

- реестр проектов;
- создание проекта;
- добавление приложений;
- команда проекта;
- состав приложения;
- React Flow-граф;
- настройки ЖЦ;
- конструктор общего релиза;
- статус готовности релизной партии.

### 6.4. Приложения

Отдельный плоский реестр всех доступных приложений:

- без обязательной привязки к выбранному КИТС;
- без обязательного входа через проект;
- новые сверху по `created_at DESC`;
- фильтр по КИТС;
- фильтр по проекту;
- фильтр по уровню;
- фильтр по статусу;
- поиск;
- Git;
- последний Build;
- переход в приложение или проект.

### 6.5. React Flow

React Flow используется внутри Project Detail для визуального графа приложений:

```text
Project Detail
├── MUI Data Grid состава
└── React Flow-граф связей
```

Граф не является отдельной декоративной витриной. Он редактирует серверную модель связей:

- выбор строки подсвечивает узел;
- выбор узла открывает приложение;
- создание ребра сохраняется на сервере;
- удаление ребра сохраняется на сервере;
- таблица и граф используют один источник данных;
- layout строится через `@xyflow/react` и `dagre`.

## 7. Minimal UI и техническая база фронтенда

### 7.1. Фактический статус

Аудит показал:

```text
В cosmoport2 сейчас:
  MUI + собственная тема + обычные MUI Table

Не доказано/не сделано:
  фактическая натяжка Minimal UI template
  полноценный MUI X Data Grid
```

В `prettyk-dev` есть реальный лицензированный контур:

```text
frontend/src/design-admin/
frontend/src/design-admin/sections/ThemeOverview.tsx
```

Упоминание Minimal UI в документации само по себе не означает, что он подключён к Cosmoport.

### 7.2. Цель

Использовать купленный Minimal UI как визуальную и компонентную основу Control Station:

- shell;
- навигация;
- page header;
- карточки;
- формы;
- фильтры;
- таблицы;
- Data Grid;
- dialogs;
- drawers;
- status chips;
- loading/error/empty states;
- Project Detail;
- Application Detail.

Не нужно импортировать всё подряд. Нужно использовать все нужные нам компоненты и выдержать единую эстетику шаблона.

```text
Minimal UI / MUI → Control Station
Tailwind / Radix / Monaco / xterm → Web IDE
@xyflow/react → Project Graph
```

Pure Box и Cosmoport используют общую лицензионную дизайн-основу, но не внутренние модули и не общую БД.

### 7.3. Таблицы

Для крупных реестров целевая база — MUI X Data Grid:

- серверная пагинация;
- сортировка;
- фильтры;
- поиск;
- закрепление колонок;
- выбор колонок;
- density;
- переходы по строкам;
- честные пустые и ошибочные состояния.

Обычный `MUI Table` может остаться для небольших вложенных таблиц, но не должен быть основной основой реестров приложений и проектов.

## 8. Приложение, Pipeline и локальный ЖЦ

### 8.1. Приложение

Приложение — техническая карточка внутри одного или нескольких проектов.

Она содержит:

- app-code;
- название;
- уровень L0/L1/L2;
- проектные связи;
- КИТС-теги;
- команды;
- Git binding;
- pipeline/plan;
- настройки ЖЦ;
- типы релизов;
- сборки;
- локальные деплои в текущей зоне;
- релизы;
- Findings/Evidence.

### 8.2. Связь приложений

Руководитель разработки строит структуру:

```text
L2 включает L1
L1 включает L0
```

Это не просто визуальная группировка. Связи влияют на:

- порядок сборки;
- зависимые приложения;
- состав релизной партии;
- выборку затронутых компонентов;
- граф проекта.

### 8.3. Cosmo-managed шаги

Cosmo управляет собственными шагами, например:

```text
Build
Unit Tests
Documentation
SonarQube
Trivy
CodeScoring
SBOM / CycloneDX
Deploy в текущую ЗР
```

Точный список и порядок должны задаваться профилем типа релиза и сверяться со скрейпом.

### 8.4. PrettyK-managed шаги

Следующие проверки выполняет PrettyK:

```text
Выполнение автотестов
OWASP ZAP
```

Они не должны превращаться во внутренние Cosmo-исполнители, фальшивый SSE или клиентские симуляторы.

Cosmo получает от PrettyK:

- внешний идентификатор проверки;
- статус;
- ссылку;
- Evidence;
- акт;
- итоговый `PASS`/`FAIL`.

### 8.5. ЖЦ зависит от типа приложения и артефакта

Жизненный цикл нельзя задавать одним одинаковым списком для всех приложений проекта.
Профиль выбирается как минимум по двум признакам:

```text
тип приложения / уровень
+ тип выпуска
+ фактический тип поставляемого артефакта
→ resolved lifecycle
```

Критическое правило: шаги должны соответствовать тому, что реально передаётся в сборке.

#### Source code

Для обычного исходного кода применяются проверки исходников:

```text
Build
→ Unit Tests
→ Documentation (если включена профилем)
→ SonarQube
→ CodeScoring
→ SBOM
→ Deploy в ЗР
```

Обычный source-code артефакт **не отправляется на KCS/Trivy как на контейнерный
артефакт**. Не нужно запускать нерелевантные проверки только потому, что они есть
в глобальном каталоге.

#### Docker/container image

Для контейнерного артефакта профиль другой:

```text
Build / image build
→ SBOM
→ Trivy
→ KCS
→ Deploy в ЗР
```

Docker-образ не нужно прогонять через SonarQube или CodeScoring как через проверку
исходного кода, если в конкретном профиле нет отдельного обоснования для проверки
сопутствующего source tree.

В общем batch проекта разные приложения могут иметь разные артефакты и разные
профили ЖЦ. Batch не должен насильно применять один набор проверок ко всем
приложениям.

## 9. Тип приложения и Тип релиза

### 9.1. Тип приложения

Примеры из легаси-методики:

```text
L0 — Модуль / библиотека
L1 — Линкор (Универсальное)
L2 — верхний прикладной уровень
```

В старом справочнике также встречаются типы вроде Буксира, Вселенной, Карго, Космостанции, Гипериона, Реликта и шаблонных сущностей. Их нужно учитывать как каталог видов приложений, но не переносить «Группирующий уровень» как замену Project.

### 9.2. Тип релиза

Тип релиза — это переиспользуемый профиль процесса выпуска.

Для L1 «Линкор» могут существовать:

```text
Обычный релиз Линкора
Ускоренный релиз Линкора
Регламентный релиз Линкора
Hotfix Линкора
Пользовательский тип релиза Линкора
```

Тип релиза задаёт:

- набор шагов;
- обязательность;
- порядок;
- реакцию на ошибку;
- Gates;
- Evidence;
- PrettyK DAST/QG-проверки;
- правила упаковки;
- допустимые маршруты.

### 9.3. Примеры профилей

Обычный релиз может быть полным:

```text
Build
→ Unit Tests
→ Documentation
→ SonarQube
→ Trivy
→ CodeScoring
→ SBOM
→ Deploy в ЗР
→ PrettyK Autotests
→ PrettyK ZAP
→ Gate
→ Release Package
```

Ускоренный может, например, не включать SonarQube:

```text
Build
→ Unit Tests
→ Trivy
→ SBOM
→ Deploy в ЗР
→ PrettyK QG
→ Release Package
```

Hotfix может иметь целевой набор проверок, но сам факт Hotfix не должен автоматически обходить обязательный security/QG-контур.

### 9.4. Профиль и snapshot

Тип релиза хранится как отдельная переиспользуемая сущность. При создании релиза профиль фиксируется:

```text
Release
├── release_type_id
├── release_type_version
└── resolved_lifecycle_snapshot
```

Изменение типа релиза не меняет задним числом уже созданные релизы.

Профиль может включать как Cosmo-managed, так и PrettyK-managed шаги:

```text
executor = cosmo | prettyk
```

### 9.5. Пользовательские типы

Пользовательские типы релиза можно создавать через Release Type Builder:

- выбрать применимые типы приложений и уровни;
- выбрать шаги;
- включить/отключить необязательные проверки;
- задать порядок;
- настроить `continue`/`terminate`;
- задать Gates;
- указать PrettyK-проверки;
- сохранить версию профиля.

Обычный пользовательский override не должен обходить обязательные security/QG-инварианты. Кто именно создаёт типы и кто может отключать конкретные проверки — отдельное policy-решение.

## 10. Индивидуальные релизы

Каждое приложение имеет собственный релиз:

```text
Application
  → Release Type
  → Lifecycle Profile
  → Build
  → Run
  → Findings
  → Evidence
  → Gates
  → PrettyK QG
  → Release Package
```

Релиз не должен растворять несколько приложений в одном неразличимом объекте.

У каждого приложения собственные:

- Build;
- Run;
- шаги ЖЦ;
- результаты проверок;
- Evidence;
- решения Gate;
- итоговый статус.

## 11. Общий релиз проекта и Project Release Batch Constructor

Это обязательная функция уровня проекта — **MUST-HAVE**.

### 11.1. Модель

Общий релиз проекта — партия независимых приложенческих релизов:

```text
Project Release Batch
├── Release Application A
├── Release Application B
└── Release Application C
```

Это не один гигантский релиз. Каждый дочерний релиз сохраняет:

- свой тип релиза;
- свой ЖЦ;
- свой Build;
- свои Evidence;
- свои Gates;
- свой статус.

### 11.2. Конструктор

Руководитель разработки должен иметь возможность:

- выбрать приложения проекта;
- назначить тип релиза для каждого;
- выбрать общий шаблон;
- применить локальные overrides;
- увидеть связи и зависимости;
- задать порядок;
- создать очередь;
- запустить релизы последовательно или разрешёнными группами;
- увидеть блокирующее приложение;
- переиграть только неуспешный дочерний релиз;
- сформировать пакет партии.

Пример:

```text
Project PAYMENTS
├── pay-api       → Обычный релиз Линкора
├── pay-worker    → Ускоренный релиз Линкора
├── shared-lib    → Релиз библиотеки
└── antifraud     → Hotfix
```

### 11.3. Статусы партии

```text
draft
queued
running
partially_succeeded
succeeded
failed
blocked
```

Batch не является атомарной транзакцией, которая уничтожает результаты всех приложений при падении одного дочернего релиза.

## 12. PrettyK, QG и акт

### 12.1. Внешний контракт

```text
Cosmo → инициирует или запрашивает DAST-проверку
PrettyK → выполняет Autotests / OWASP ZAP
PrettyK → возвращает PASS или FAIL
PrettyK → возвращает Evidence и акт
Cosmo → прикладывает акт к релизному архиву
```

Cosmoport не импортирует модули Pure Box и не копирует внутрь:

- DAST engine;
- Fuzzer;
- Playwright internals;
- scanner internals;
- PrettyK Admin implementation.

### 12.2. Gate готовности

Релизный пакет разблокируется только если:

```text
обязательные Cosmo-шаги = PASS
PrettyK DAST/QG = PASS
обязательные Gates = PASS
Evidence собрано
акт приложен
```

Без DAST/QG:

```text
не готово к передаче
```

## 13. Release Package, СОД, МЗП и маршруты

### 13.1. Граница текущего ЗР-инстанса

Cosmoport ЗР формирует пакет и показывает:

```text
Ready for transfer
```

Он не обязан в текущем scope сам перемещать пакет в ЗТ.

### 13.2. Состав пакета

Пакет содержит:

- идентификатор проекта;
- приложения и дочерние релизы;
- типы релизов и версии профилей;
- commit SHA;
- результаты Build;
- результаты ЖЦ;
- Findings/Evidence;
- PrettyK DAST/QG verdict;
- акт в архиве;
- контрольные суммы;
- версию формата пакета;
- маршрут.

### 13.3. Маршрут

Маршрут означает, в какой кластер СОД/МЗП направлять пакет.

```text
Cosmo → route id + release package
СОД/МЗП → знает физический кластер и правила доставки
```

Cosmo не обязан знать, что условный КЦОИ соответствует конкретной airgap-сети. Эта карта принадлежит СОД/МЗП.

### 13.4. Future epics

Отдельно исследуются и реализуются:

- transfer table;
- маршруты;
- СОД;
- МЗП;
- архивный формат;
- межзоновая доставка;
- отдельный Cosmoport ЗТ;
- отдельный Cosmoport ЗПЭ.

Для этого нужен отдельный аудит Cosmoport 1.0 и дополнительные скрейпы. Не надо сейчас выдумывать внутреннюю механику непроисследованных передатчиков.

## Artifact Registry Layer — Nexus / Artifactory / Т1-Сфера

В текущей модели не хватало слоя артефактов. Cosmoport должен работать не только
с Git и Build, но и с registry, в котором лежат контейнерные образы, SBOM и
остальные релизные артефакты.

```text
Source / Build
  → Artifact Registry
  → релевантные проверки
  → Release
  → Deployment по immutable digest
```

### Целевая стратегия

Свой registry не пишем. Cosmoport использует нейтральный `ArtifactRegistry`
adapter и поддерживает провайдеров:

```text
nexus
artifactory
t1_sfera
```

Выбор провайдера задаётся конфигурацией конкретного инстанса, зоны и/или
namespace. Nexus и Artifactory нужны как рабочие integration targets и
переходный контур. Т1-Сфера закладывается как отечественный first-class provider
для будущих поставок в ЦБ и PrettyK bundle.

### Почему Т1-Сфера

Её использование в закрытом контуре логично объясняется:

- импортозамещением после 2022 года;
- снижением зависимости от внешних поставщиков;
- on-premise и airgap-размещением;
- контролем цепочки поставки образов;
- локальной поддержкой и регуляторными требованиями.

При этом переход может быть постепенным: часть потоков остаётся на Nexus или
Artifactory, часть переводится в Т1-Сферу. Cosmoport должен поддерживать mixed
mode и не делать Nexus единственным backend.

### Adapter contract

Предварительный нейтральный контракт:

```text
push_artifact()
pull_manifest()
resolve_digest()
check_artifact()
copy_or_promote()
get_sbom_reference()
```

Сначала проверяем, поддерживает ли Т1-Сфера OCI/Docker Registry V2. Если да,
отдельная сложная интеграция не нужна: используется общий OCI adapter. Если API
проприетарный, добавляется тонкий REST adapter по официальной документации.

Никакого копирования или несанкционированного извлечения продукта не делаем:
только официальная поставка, документация, доступный API или легальная trial
лицензия.

### Artifact metadata

Build и Release должны фиксировать:

- `registry_id`;
- provider;
- repository;
- artifact/image name;
- tag;
- immutable digest;
- media type;
- размер;
- SBOM reference;
- scan references;
- signature/attestation, если поддерживается.

Релиз и деплой ссылаются на digest, а не только на mutable tag вроде `latest`.
В БД хранятся только secret references (`vault:secret/...`, `openbao:secret/...`).

### Registry по зонам

```text
Cosmoport ЗР  → Registry ЗР
Cosmoport ЗТ  → Registry ЗТ
Cosmoport ЗПЭ → Registry ЗПЭ
```

В текущем scope Cosmoport ЗР работает с Registry ЗР. Физическое перемещение
образов между зонами остаётся будущей ответственностью СОД/МЗП или отдельного
zone-transfer контура.

### Artifact-aware lifecycle

Тип артефакта определяет релевантные проверки:

```text
Source code
  → SonarQube / CodeScoring / SBOM
  → без KCS/Trivy как container scan

Docker/container image
  → SBOM / Trivy и/или KCS
  → без SonarQube/CodeScoring как source scan
```

В одном Project Release Batch разные приложения могут иметь разные артефакты,
registry namespace и профили ЖЦ.

- Autotests;

## 18. Принципы честной реализации

Любая новая функция принимается только если:

- данные приходят из API/БД, а не из локальных генераторов;
- ошибка бэкенда видна оператору;
- фильтр не подменяет authorization;
- состояние релиза можно восстановить из PostgreSQL;
- профиль релиза версионируется и снапшотится;
- DAST выполняется PrettyK, а не имитируется Cosmo;
- React Flow редактирует серверный граф;
- Project и Application не смешиваются;
- КИТС остаётся тегом;
- зоны не смешиваются в одну БД;
- внутренние модули Pure Box не импортируются;
- UI использует Minimal UI-паттерны, а не случайный самописный MUI-набор;
- пустой список показывает EmptyState;
- loading показывает loading state;
- ошибка показывает error state;
- тесты проверяют реальный контракт, а не только наличие текста на экране.
