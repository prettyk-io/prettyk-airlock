# 🏛️ Cosmoport 2.0: План правильного жизненного цикла (plan_correct_lifecycle.md)

> **Статус:** Живой канонический документ (Living Architecture Document).  
> **Назначение:** Единый источник правды по доменной модели графов, типам релизов, композиции ЖЦ и поведению сущностей. Будет регулярно дополняться и патчиться по мере скрапинга фронта старого Cosmoport и поступления новых требований.  
> **Основа:** Discovery `BEMR v3.8`, `BEWS/BELS v2.13`, опыт Pure Box и каноны Обители.  
> **Главный вектор:** *«Заменяем монструозную жесткую иерархию (2 группирующий > 2 > 1 > 0) и уродливые формы на чистый типизированный граф (DAG), сохраняя глубокую семантику типов релизов и управления жизненным циклом»*.

---

## 1. Доменная иерархия и графовая модель (Graph Topology)

Вместо старой жесткой вложенности папок («группирующее пространство 2 уровня → 2 → 1 → 0») Cosmoport 2.0 разделяет:

### 1.1. Инфраструктурно-доменные границы
```text
Кластер (Сеть / Зона: ЗР (Dev) ──> ЗТ (Test) ──> ЗПЭ (Prod))
  └── КИТС (Бизнес-домен / Команда / Квоты / Доменный RBAC)
        └── Проект (Система / Логический комплекс сервисов)
```

### 1.2. Граф связей приложений и компонентов (Application DAG)
Внутри Проекта/КИТС приложения связываются как узлы ориентированного графа:

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              Application Topology Graph                                │
│                                                                                        │
│     [ L0: lib-auth ] ────────── uses_library ──────────┐                               │
│     (Shared Repo)                                      ▼                               │
│                                              [ L1: payment-api ]                       │
│     [ L0: orbit-config ] ─── uses_library ──>  (1 App = 1 Git)                         │
│                                                        │                               │
│                                                   runtime_link                         │
│                                                        │                               │
│                                                        ▼                               │
│     [ L0: lib-crypto ] ───── uses_library ──> [ L1: crypto-worker ]                    │
│                                                        │                               │
│                                                     contains                           │
│                                                        ▼                               │
│                                              ┌───────────────────┐                     │
│                                              │ L2: Composite Hub │                     │
│                                              └───────────────────┘                     │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

## 2. Типология узлов (Node Levels & Kinds)

| Уровень | Смысловой тип (Kind) | Назначение | Требует деплоя? | Git-репозиторий |
|---|---|---|---|---|
| **Level 0** | `library` (Модуль) | Переиспользуемая библиотека (Java, Go, Python, TS) | ❌ Нет | Собственный репозиторий |
| **Level 0** | `config_template` (Орбиты) | Шаблоны конфигураций / etcd / Helm values | ❌ Нет | Собственный репозиторий |
| **Level 0** | `report_template` (Астрокарта) | Шаблоны отчетов и печатных форм | ❌ Нет | Собственный репозиторий |
| **Level 0** | `data_helper` (Буксир) | SQL-скрипты миграций, вспомогательные данные | ❌ Нет (опционально) | Репозиторий или бакет |
| **Level 1** | `service` (Линкор / Челнок) | Атомарный микросервис / backend / frontend | ✅ Да | 1 приложение = 1 Git-репозиторий |
| **Level 1** | `legacy_app` (Реликт) | Унаследованное приложение / монолит | ✅ Да | Внешний / связанный репозиторий |
| **Level 1** | `service_subsystem` (СПС) | Платформенная / сервисная подсистема | ✅ Да | Собственный репозиторий |
| **Level 2** | `composite_group` | Композитный бандл / мета-проект группы сервисов | ✅ Оркестрация | Pipeline-only репозиторий |

## 3. Типизированные ребра графа (Edge Types)

Связи между компонентами имеют явный тип и правила валидации:

1. **`contains` (Структурное включение):** узел L2 включает в свой состав сервисы L1.
2. **`uses_library` (Зависимость от L0):** сервис L1 использует библиотеку/шаблон L0. При выходе новой версии L0 система генерирует рекомендацию к обновлению.
3. **`depends_on` (Порядок сборки и деплоя):** строгий порядок прогона: узел B не начинает сборку/деплой, пока узел A не завершил этап и не прошел гейты.
4. **`runtime_link` (Сетевая связность):** указание на то, что сервис A вызывает сервис B в рантайме (необходимо для проброса DAST/fuzzer контекстов).
5. **`hard_pin` vs `soft_pin`:**
   - `hard_pin`: зафиксирован точный git commit SHA / семантический тег (обязательно для Prod-релизов).
   - `soft_pin`: плавающая ссылка (`branch: main`, `latest-stable`) для динамической сборки в Dev-контуре.

## 4. Схема управления релизами (BEMR Synthesis)

Релиз — это **не просто строчка со статусом в базе**, а криптографически зафиксированный слепок графа на определенный момент времени.

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                             Release Snapshot (v2.4.0)                                  │
├────────────────────────────────────────────────────────────────────────────────────────┤
│  Release Type: "Hotfix" | "Standard" | "Quarterly Major"                               │
│  Release Scope: Composite Payment Hub (Level 2)                                        │
│  Target Envelope: ЗР (Dev) ──> ЗТ (Test) ──> ЗПЭ (Prod)                                │
├────────────────────────────────────────────────────────────────────────────────────────┤
│  PINNED GRAPH NODES:                                                                   │
│  • payment-api: git@gitea:payments/api.git @ commit 8a4f12 (v2.4.0)                    │
│  • crypto-worker: git@gitea:payments/crypto.git @ commit 3c91e0 (v1.8.2)               │
│  • lib-auth: git@gitea:shared/lib-auth.git @ commit f412b1 (v1.2.0)                   │
│                                                                                        │
│  LIFECYCLE & SECURITY GATES APPLIED:                                                   │
│  • Gate 1: Static Severity (Threshold: 0 Crit, max 2 High) ──> 🟢 PASSED              │
│  • Gate 2: Deploy Readiness (Health probe /live) ───────────────> 🟢 PASSED            │
│  • Gate 3: Dynamic Severity (DAST + Fuzzer) ────────────────────> 🟢 PASSED            │
│  • Gate 4: Admission Gate (Human signature: sec_expert) ────────> ✍️ SIGNED            │
│                                                                                        │
│  EVIDENCE MERKLE ROOT: sha256:9f8e7d6c5b4a...                                          │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 4.1. Типы релизов (Release Types)
Каждый КИТС / Проект может определять кастомные типы релизов:
- **`Hotfix`:** ускоренный ЖЦ, точечный скоуп (1–2 сервиса), обязательный SAST + быстрый смоук, блокировка широкого регресса.
- **`Standard (Плановый)`:** полный конвейер (SAST + SCA + DAST + Fuzzer + Autotests), прохождение всех гейтов.
- **`Major / Quarterly (Квартальный)`:** комплексный композитный релиз Level 2, включающий десятки сервисов и библиотек, обязательный ГОСТ-Акт и подпись ИБ-лидера.

**Инвариант:** как только с типом релиза был создан хотя бы один реальный релиз, тип релиза переходит в статус `sealed` (не может быть удален или деструктивно изменен).

### 4.2. Комплексирование и селективная пересборка («Перезапускать сборку»)
При создании релиза составной системы (L2):
1. Платформа собирает граф всех зависимых L1 и L0.
2. Для каждого включенного компонента действует флаг **`rebuild_on_trigger` (Перезапускать сборку)**:
   - Если флаг активен → при запуске релизного конвейера зависимый компонент пересобирается с нуля и генерирует свежий артефакт.
   - Если флаг выключен → переиспользуется готовый запечатанный артефакт по его `content_hash` из ArtifactStore / MinIO.

### 4.3. Портативный JSON-манифест релиза
Состав релиза сериализуется в единый валидируемый JSON-манифест:
```json
{
  "release_version": "2.4.0",
  "release_type": "standard",
  "domain_id": "digital-ruble",
  "project_id": "payment-hub",
  "nodes": [
    { "id": "payment-api", "level": 1, "commit_sha": "8a4f12", "rebuild": true },
    { "id": "lib-auth", "level": 0, "commit_sha": "f412b1", "rebuild": false }
  ],
  "edges": [
    { "source": "lib-auth", "target": "payment-api", "type": "uses_library" }
  ],
  "gates_policy": {
    "max_critical_findings": 0,
    "require_manual_admission": true
  }
}
```
Манифест используется для чистого межзонного трансфера (`ЗР → ЗТ → ЗПЭ`) без передачи дампов базы.

## 5. Политики наследования прав и интеграций

1. **Права команды (RBAC):**
   - Настраиваются на уровне КИТС и действуют на вложенные проекты.
   - `Merge (Объединение):` локальные права суммируются с правами КИТС (превалирует более строгая роль).
   - `Isolate (Изоляция):` проект имеет изолированную команду.
2. **Интеграции (Forge, CI, Vault):**
   - Настраиваются на уровне КИТС/Кластера и безопасно пробрасываются в пайплайны.
   - Сервисы не хранят явные креды — получают scoped tokens на время исполнения через `CapabilityBroker`.

## 6. Отображение на 8 сущностей в PostgreSQL

```text
cosmo_domains        ── КИТС (границы доменов, квоты, настройки типов релизов)
cosmo_applications   ── Узлы графа (Level 0, 1, 2 с repo_binding, JSONB-связями)
cosmo_pipelines      ── Шаблоны пайплайнов и конфигурации шагов ЖЦ
cosmo_runs           ── Экземпляры выполнения (Run), зафиксированный compiled_plan
cosmo_batches        ── Пачки шагов (Build / Static Scan / Deploy / Dynamic Test)
cosmo_findings       ── Нормализованные уязвимости с привязкой к ноде графа и run_id
cosmo_evidence_ledger── Иммутабельная SHA-256 цепочка улик и манифестов
cosmo_audit_events   ── Аудит создания типов релизов, утверждения гейтов и трансферов
```

## 7. UI/UX: Графовый интерактив вместо модального ада

В **Control Station (MUI + @xyflow/react)**:
- **Интерактивный Canvas топологии:** наглядное соединение стрелками L0 библиотек с L1 сервисами.
