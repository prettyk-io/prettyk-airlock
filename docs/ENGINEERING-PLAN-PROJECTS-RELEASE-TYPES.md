# Cosmoport 2.0 — инженерный план Projects, Release Types и Steel Thread

> **Статус:** engineering draft / SoT для следующей волны планирования  
> **Дата:** 30 августа 2026  
> **Текущий scope:** один инстанс Cosmoport в зоне разработки (ЗР) одной закрытой airgap-сети  
> **Исполнители после финальной нарезки:** Boss, Flash, Luna  
> **Buddy:** временно занят переносом окружений, кешей и Docker/WSL storage на `D:`

---

## 1. Главный архитектурный вывод

Cosmoport 2.0 не является единым межзоновым порталом и не является глобальным мультитенантным Control Plane.

Целевая модель:

```text
Одна закрытая airgap-сеть / кластер
└── один локальный инстанс Cosmoport для одной зоны
    ├── собственная PostgreSQL
    ├── собственный Gitea
    ├── собственный локальный PrettyK-контур
    └── собственная конфигурация инстанса
```

Текущий инстанс:

```text
Платформа: ПлЦР
Зона: ЗР
Инстанс: Cosmoport ЗР
```

ПлЦР не зашивается в код. Это конфигурация конкретной поставки.

В будущем могут существовать отдельные копии:

```text
Cosmoport ЗР  → отдельный хост, БД, Gitea
Cosmoport ЗТ  → отдельный хост, БД, Gitea
Cosmoport ЗПЭ → отдельный хост, БД, Gitea
```

У разных зон могут быть разные airgap-сети. Единого межсеточного Cosmoport не планируется.

### 1.1. Контракт с PrettyK

Cosmoport не импортирует внутренние модули Pure Box. Связь только через:

- REST;
- webhook;
- SSE;
- внешний идентификатор проверки;
- внешний результат `PASS` / `FAIL`;
- акт и Evidence.

PrettyK может быть полноценной коробкой или минимальным раннером DAST. Cosmoport не должен зависеть от внутреннего устройства поставки.

## 2. Зоны и граница текущего scope

Скрейпнутый портал — это портал **зоны разработки (ЗР)** и только ЗР.

ЗТ и ЗПЭ — другие порталы, на других хостах, со своими Gitea и своими конфигурациями. Их UI и процессы будут исследоваться и реализовываться позднее по отдельным скрейпам.

Текущий Cosmoport ЗР отвечает за:

```text
Проект
→ Приложения
→ Git
→ Pipeline / Plan
→ Build
→ Run
→ Findings / Evidence
→ Gates
→ PrettyK DAST/QG
→ Release
→ Release Package
→ Ready for transfer
```

Текущий Cosmoport ЗР **не отвечает** за фактическую доставку пакета в ЗТ.

Жизненный цикл текущего инстанса заканчивается здесь:

```text
Release Package сформирован,
акт приложен,
все обязательные проверки пройдены,
пакет готов к передаче через sovereign cross-zone transport или СОД bridge.
```

Sovereign transport и СОД bridge пока не моделируем глубоко. Это будущие отдельные
эпики после получения внешних contracts. МЗП исключён.

## 3. Domain и КИТС

### 3.1. Domain не является целевой бизнес-сущностью

Текущая модель с `Domain`, обязательным `X-Cosmo-Domain` и жёсткой domain-изоляцией была построена на неверной предпосылке.

В целевой модели:

```text
Instance Config = локальный контекст поставки
КИТС = тег приложения
```

Нужно постепенно убрать использование `Domain` как:

- tenant boundary;
- обязательного контекста каждого GET-запроса;
- замены КИТС;
- механизма определения зоны;
- механизма выбора Gitea.

Конфигурация инстанса должна содержать примерно:

```text
COSMO_INSTANCE_ID
COSMO_NETWORK_ID
COSMO_ZONE
COSMO_PLATFORM_LABEL
COSMO_FORGE_URL
COSMO_PRETTYK_URL
```

Значения вроде `plcr`, `ПлЦР`, URL Gitea и адрес PrettyK — только конфигурация.

### 3.2. КИТС — many-to-many tags

КИТС — классификационный тег, которым помечают приложения.

```text
Application ←→ KITS tags
```

Одно приложение может иметь несколько КИТС-тегов.

КИТС используется для:

- фильтрации;
- сортировки;
- проектной агрегации;
- автоматической видимости Администратора КИТС;
- аналитики.

КИТС не должен создавать:

- отдельную БД;
- отдельную зону;
- отдельный Gitea;
- жёсткую межтенантную границу;
- обязательный header для чтения.

Переключатель КИТС в интерфейсе — это фильтр:

```text
Все доступные КИТС
КИТС-1
КИТС-2
...
```

При выборе «Все» пользователь видит весь набор, доступный ему по ролям и членству.

## 4. Проект — главная сущность оператора

### 4.1. Зачем нужен Project

В старом портале есть четыре категории:

```text
Нулевой уровень
Первый уровень
Второй уровень
Группирующий уровень
```

«Группирующий уровень» фактически является костылём для контейнера связанных приложений. В Cosmoport он заменяется полноценным `Project`.

### 4.2. Целевая структура

```text
Project
├── Application L2
│   ├── Application L1
│   │   ├── Application L0
│   │   └── Application L0
│   └── Application L1
└── другие приложения проекта
```

Правила:

- L0/L1/L2 — уровень или тип приложения;
- «Группирующий уровень» удаляется;
- любое приложение получает проект;
- одиночное L0-приложение тоже создаётся внутри проекта;
- приложение может входить в несколько проектов;
- связи между приложениями — отдельные рёбра графа;
- Project не равен старой Group.

Проект может быть создан без приложений. Тогда он должен содержать метаинформацию:

- назначение;
- обоснование создания;
- владелец;
- предполагаемый состав;
- область ответственности;
- статус;
- дату создания;
- планируемые приложения.

Проект изначально создаёт ИТ-лидер.

### 4.3. Проект и репозитории

Проект не обязан иметь собственный репозиторий:

```text
Project
├── Application A → Repository A
├── Application B → Repository B
└── Application C → Repository C
```

ИТ-лидер создаёт приложения и инициирует создание или подключение отдельных Gitea-репозиториев в текущей зоне.

## 5. Команды и видимость

### 5.1. Два уровня команд

Команды существуют на уровне проекта и приложения:

```text
Project Team
Application Team
```

При пакетном назначении из проекта:

```text
Project Team
→ базовый состав для приложений проекта
→ индивидуальные Application Team overrides
```

Для приложения можно:

- добавить участника;
- исключить участника;
- изменить его роль;
- оставить проектную роль;
- задать индивидуальное разрешение.

Система должна различать унаследованных и локально назначенных участников.

### 5.2. Ролевая модель

#### Администратор ИБ

Это не обычный член команды приложения.

Администратор ИБ — владелец финального PrettyK DAST/QG-контура:

- сам открывает нужные проекты;
- видит всё необходимое для контроля;
- управляет финальными QG/DAST-решениями;
- не должен добавляться ИТ-лидером;
- не должен зависеть от ручного включения в team;
- без его допустимого QG-результата релиз не считается готовым к передаче.

#### Администратор КИТС

Если приложение имеет КИТС-тег Администратора:

```text
Администратор КИТС автоматически видит весь проект.
```

Но видимость разделяется:

```text
Приложения с его КИТС:
  полноценная работа по полномочиям

Остальные приложения проекта:
  readonly-превью
  не кликабельны
  доступны только название и app-code
```

Администратор КИТС не получает автоматически полномочия Администратора ИБ.

#### Эксплуатационные администраторы

Глобальную видимость имеют:

- Администратор НШР;
- `admin_service`;
- обычный системный администратор;
- Администратор ИБ.

Эти роли уже в значительной степени определены в PrettyK. В Cosmoport реализуется только необходимый RBAC-контур и рабочий административный интерфейс, а не вторая независимая админская платформа.

#### ИТ-лидер

ИТ-лидер:

- создаёт проект;
- создаёт приложения;
- назначает КИТС-теги;
- инициирует создание репозиториев;
- задаёт начальные метаданные.

Он не обязан добавлять Администратора ИБ или Администратора КИТС.

#### Руководитель разработки

Руководитель разработки:

- строит связи приложений;
- работает с графом проекта;
- создаёт индивидуальные релизы;
- создаёт общий batch-release проекта;
- определяет состав релизной партии.

#### Команда приложения

Команда:

- работает с кодом в отдельных репозиториях;
- запускает сборки;
- получает результаты ЖЦ;
- иногда использует Web IDE;
- видит приложения, в командах которых состоит.

### 5.3. Базовое правило видимости

```text
Видит приложение, если:
  пользователь входит в команду приложения
  ИЛИ пользователь — Администратор КИТС его тега
  ИЛИ пользователь — глобальный администратор
```

Visibility — это серверное правило. UI-фильтр КИТС не заменяет authorization.

## 6. Навигация и поверхности UI

### 6.1. Sidebar

```text
Обзор
Проекты
Приложения
Пайплайны
Прогоны
Гейты
Релизы
Сборки
Деплои
```

### 6.2. Обзор

Главная таблица показывает проекты, а не миллион приложений.

Минимальный состав:

- проект;
- КИТС-теги;
- количество приложений;
- распределение L0/L1/L2;
- руководитель разработки;
- статус;
- последний релиз;
- дата обновления;
- действия.

### 6.3. Проекты

Основная операторская поверхность:

- реестр проектов;
- создание проекта;
- добавление приложений;
- команда проекта;
- состав проекта;
- React Flow-граф;
- настройки ЖЦ;
- конструктор общего релиза;
- статус готовности пакета.

### 6.4. Приложения

Плоский полный реестр доступных приложений:

- сортировка по `created_at DESC`;
- фильтр по проекту;
- фильтр по КИТС;
- фильтр по уровню;
- фильтр по статусу;
- поиск;
- Git;
- последний Build;
- переход в проект или карточку приложения.

### 6.5. React Flow

React Flow используется для графа связей внутри проекта. Он не заменяет таблицу.

```text
Project Detail
├── MUI Data Grid состава проекта
└── React Flow-граф зависимостей
```

Обязательная синхронизация:

- выбор строки подсвечивает узел;
- выбор узла открывает приложение;
- изменение связи обновляет сервер;
- таблица и граф перечитывают одни и те же данные;
- декоративных локальных графов нет.

### 6.6. Minimal UI

Фактический аудит показал:

```text
В текущем репозитории PrettyK Control Plane сейчас:
  MUI + собственная тема + обычные MUI Table

Фактически не подключены:
  лицензированный Minimal UI как основа
  MUI X Data Grid
```

В `prettyk-dev` есть реальный контур лицензированного Minimal UI:

```text
frontend/src/design-admin/
frontend/src/design-admin/sections/ThemeOverview.tsx
```

Цель следующей UI-волны:

- использовать весь нужный потенциал купленного Minimal UI;
- взять его как основу форм, карточек, таблиц, фильтров и shell-паттернов;
- подключить MUI X Data Grid;
- сохранить Meta Light по умолчанию;
- адаптировать компоненты в Cosmoport;
- не импортировать внутренние модули Pure Box;
- не смешивать MUI Control Station и Tailwind Web IDE.

```text
Minimal UI / MUI → Control Station
Tailwind / Radix / Monaco → Web IDE
@xyflow/react → граф проектов
```

Лицензия общая, продукты и кодовые контуры остаются раздельными.

## 7. Тип приложения и Тип релиза

Это две разные сущности.

### 7.1. Тип приложения

Например:

```text
L0 — Модуль / библиотека
L1 — Линкор (Универсальное)
L2 — прикладной верхний уровень
```

Тип приложения определяет свойства карточки и допустимые профили выпуска.

### 7.2. Тип релиза

Тип релиза — переиспользуемый профиль процесса выпуска:

```text
Обычный релиз Линкора
Ускоренный релиз Линкора
Регламентный релиз Линкора
Hotfix Линкора
Пользовательский тип релиза Линкора
```

Он определяет:

- набор шагов;
- обязательность шагов;
- порядок;
- реакцию на ошибку;
- обязательные Gates;
- требования к Evidence;
- PrettyK-проверки;
- условия упаковки;
- допустимый маршрут передачи.

В конструкторе индивидуального и общего релиза пользователь выбирает созданный тип релиза.

## 8. Lifecycle Profiles

Текущий `LifecycleResolver` с базовым каталогом из 8 Cosmo-шагов не выбрасывается. Его роль меняется.

```text
Canonical Step Catalog
  → доступные шаги

Application Kind / Level
  → применимость

Release Type
  → конкретный профиль

Application overrides
  → локальные изменения

LifecycleResolver
  → resolved lifecycle конкретного релиза
```

Нельзя считать, что каждый релиз всегда имеет одинаковые 8 шагов.

Базовый каталог Cosmo включает управляемые в Cosmo проверки вроде:

```text
Build
Unit Tests
Documentation
SonarQube
Trivy
CodeScoring
SBOM
Deploy в ЗР
```

Точный канонический состав и порядок должны быть сверены с текущим скрейпом и типами релизов.

### 8.1. PrettyK-шаги

Следующие проверки принадлежат PrettyK:

```text
Выполнение автотестов
OWASP ZAP
```

Они не реализуются как внутренние исполнители Cosmo. В профиле релиза они представлены как внешние проверки:

```text
executor = prettyk
```

Cosmo хранит:

- внешний идентификатор проверки;
- статус;
- ссылку на PrettyK;
- Evidence;
- акт;
- итоговый QG verdict.

## 9. Релизы

### 9.1. Релиз принадлежит приложению

У каждого приложения собственные:

- релиз;
- тип релиза;
- Lifecycle Profile;
- Build;
- Run;
- Findings;
- Evidence;
- Gate Decisions;
- PrettyK result.

### 9.2. Снимок профиля

При создании релиза профиль типа релиза фиксируется:

```text
Release
├── release_type_id
├── release_type_version
└── resolved_lifecycle_snapshot
```

Изменение типа релиза не должно задним числом менять уже созданный релиз.

### 9.3. Обычный, ускоренный, регламентный и Hotfix

Обычный релиз Линкора может содержать полный профиль.

Ускоренный профиль может, например, не включать SonarQube, если это разрешено политикой профиля.

Hotfix может использовать целевые проверки, но не должен автоматически обходить обязательный security/QG-контур.

Без допустимого DAST/QG-результата от PrettyK релизный пакет не считается готовым к передаче.

## 10. Project Release Batch Constructor — MUST-HAVE

Это не один общий гигантский релиз. Это партия независимых релизов приложений.

```text
Project Release Batch
├── Release Application A
├── Release Application B
└── Release Application C
```

Каждый дочерний релиз сохраняет собственные:

- тип релиза;
- ЖЦ;
- Build;
- Evidence;
- Gates;
- результат.

Конструктор проекта должен позволять:

- выбрать приложения;
- назначить тип релиза для каждого;
- выбрать общий шаблон с локальными overrides;
- увидеть зависимости;
- задать порядок и очередь;
- запускать приложения последовательно или по разрешённым группам;
- видеть блокирующее приложение;
- переигрывать только неуспешный дочерний релиз;
- сформировать единый пакет с отдельными релизами внутри.

Предварительное имя сущности:

```text
ReleaseBatch
```

Финальное имя и поля сверяются с Cosmoport 1.0.

Batch не должен быть атомарной транзакцией, уничтожающей результаты соседних приложений.

Предварительные статусы партии:

```text
draft
queued
running
partially_succeeded
succeeded
failed
blocked
```

## 11. Release Package, cross-zone transport и СОД bridge

После прохождения ЖЦ и QG Cosmo формирует пакет:

- идентификатор проекта;
- состав приложений;
- идентификаторы дочерних релизов;
- выбранные типы релиза;
- commit SHA;
- результаты Build и шагов ЖЦ;
- Findings/Evidence;
- PrettyK DAST verdict;
- акт в архиве;
- контрольные суммы;
- версия формата пакета;
- идентификатор маршрута.

Маршрут означает target-zone context и выбранный transport provider. Он не
означает, что Cosmo сам знает физическую карту сетей.

```text
Cosmo → route id + package
sovereign transport / СОД bridge → знает доставку
```

Transfer table, маршрутизация, sovereign transport и СОД bridge — будущие отдельные
крупные эпики. Для СОД bridge нужны актуальный API/operations contract и
исследование текущей поставки. МЗП исключён и не должен появиться в модели.

## 12. Целевой Steel Thread

```text
ИТ-лидер
  → создаёт Project
  → создаёт L0/L1/L2 applications
  → назначает КИТС-теги
  → инициирует отдельные Gitea repositories

Администратор КИТС
  → автоматически видит проект по тегу
  → полноценно работает со своими приложениями
  → остальные видит readonly-превью
  → назначает команды

Руководитель разработки
  → строит граф проекта
  → выбирает Release Type
  → создаёт индивидуальные релизы
  → либо создаёт Project Release Batch

Команда
  → работает в репозиториях
  → запускает Build
  → проходит индивидуальный Lifecycle Profile

Cosmo
  → записывает Findings/Evidence
  → проверяет внутренние Gates
  → получает PrettyK DAST/QG verdict
  → прикладывает акт
  → формирует Release Package
  → показывает Ready for transfer

Sovereign transport / СОД bridge
  → принимают пакет для дальнейшего перемещения
```

## 13. Целевые API-поверхности

Предварительные endpoint-группы:

```text
GET    /api/v1/instance

GET    /api/v1/kits

GET    /api/v1/projects
POST   /api/v1/projects
GET    /api/v1/projects/{id}
PUT    /api/v1/projects/{id}
GET    /api/v1/projects/{id}/apps
POST   /api/v1/projects/{id}/apps
GET    /api/v1/projects/{id}/graph
PUT    /api/v1/projects/{id}/graph
GET    /api/v1/projects/{id}/team
PUT    /api/v1/projects/{id}/team

GET    /api/v1/apps
GET    /api/v1/apps/{id}
GET    /api/v1/apps/{id}/team
PUT    /api/v1/apps/{id}/team

GET    /api/v1/release-types
POST   /api/v1/release-types
GET    /api/v1/release-types/{id}
PUT    /api/v1/release-types/{id}

GET    /api/v1/projects/{id}/release-batches
POST   /api/v1/projects/{id}/release-batches
GET    /api/v1/release-batches/{id}
POST   /api/v1/release-batches/{id}/run
```

`GET /apps` должен поддерживать фильтры:

```text
project_id
kits
level
status
search
created_from
created_to
sort
pagination
```

Сортировка по умолчанию:

```text
created_at DESC
```

Обычные GET-запросы не должны требовать `X-Cosmo-Domain`.

## 15. Minimal UI acceptance

Новая UI-волна не считается принятой, если:

- используется только самописный набор обычных MUI Table;
- нет полноценной Data Grid для реестров;
- формы не следуют визуальной системе Minimal UI;
- Project Detail не имеет связки Data Grid + React Flow;
- используется хардкод вместо API;
- нет честных error/empty/loading states;
- UI смешивает MUI и Tailwind между поверхностями.
