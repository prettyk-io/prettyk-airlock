# 🏛️ Cosmoport 2.0: Спецификация санитарной чистки и канонической ревизии (Sanitary Cleansing & Sovereign Core Spec)

> **Статус:** Проект ревизии на 2FA-утверждение Максиму (Sanctuary Revision Baseline).  
> **Основа:** Директива Sanctuary, аудит кодовой базы `D:\prettyk-control-plane`, скрап-снапшоты `D:\cosmo\cosmo-frontend-to-scrape\`, 477 HAR-запросов и 14 томов ТЗ.  
> **Диагноз:** Ликвидация последствий «обезьянника» (раздутый фасад из 35 пунктов меню, синтетические mock-генераторы `Math.random()`, псевдо-научный сай-фай из DAST-лаборатории, потеря первоклассных сущностей Builds и Deployments).  
> **Главный вектор:** *«Прекратить симуляцию, сжечь бутафорию, вернуть лаконичный операторский контур строго по исходным артефактам»*.

## 2. Канонический операторский сайдбар (Строго 6 пунктов)

Вместо раздутого меню из 35 пунктов операторский пульт Cosmoport 2.0 сокращается до **6 ключевых инженерных разделов**:

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 🏛️ COSMOPORT 2.0  Domain: [ КИТС Платежи ▼ ]   Env: [ ЗР (Dev) ▼ ]    👤 sec_expert    │
├──────────────────┬─────────────────────────────────────────────────────────────────────┤
│ 📊 1. Обзор      │                                                                     │
│ 📱 2. Приложения │                  РАБОЧАЯ ОБЛАСТЬ ВЫБРАННОГО РАЗДЕЛА                 │
│ ⚡ 3. Пайплайны  │                                                                     │
│ 🚀 4. Прогоны    │                                                                     │
│ 🛑 5. Гейты      │                                                                     │
│ 📦 6. Релизы     │                                                                     │
└──────────────────┴─────────────────────────────────────────────────────────────────────┘
```

### Назначение 6 разделов:
1. **📊 Обзор (`/overview`)**:
   - Реальные счетчики из `/api/v1/status/dashboard`: активные прогоны, сбои сборок, ожидающие ручные гейты, зарегистрированные приложения.
   - Таблица последних 10 прогонов с переходом в детали.
   - Никаких синтетических графиков и псевдо-баллов.
2. **📱 Приложения (`/applications`)**:
   - Реестр приложений домена (КИТС) в MUI X Data Grid с Tree Data: Level 0 (библиотеки/шаблоны), Level 1 (сервисы), Level 2 (группы/подсистемы).
   - Кнопка «Создать приложение» (модалка с 16 типами Kinds).
   - Переход в **Карточку Приложения (Application Detail)** со всеми вложенными вкладками.
3. **⚡ Пайплайны (`/pipelines`)**:
   - Каталог Pipeline Bricks (атомарные шаги: Build, SAST, SCA, Deploy, DAST).
   - Скомпилированные планы DAG (`@xyflow/react`) с детерминированным `compiled_hash`.
4. **🚀 Прогоны (`/runs`)**:
   - Реестр запусков конвейера (`Run`) со статусами батчей (`pending`, `running`, `passed`, `failed`, `blocked`, `cancelled`).
   - Логи выполнения из MinIO и живой SSE-поток статусов.
5. **🛑 Гейты (`/gates`)**:
   - Реестр контрольных точек безопасности (Security Gates).
   - Автоматические вердикты (по порогам CVSS/CWE) и ручные точки допуска (Admission Gates) с подписью офицера ИБ.
6. **📦 Релизы (`/releases`)**:
   - Реестр сформированных релизных бандлов.
   - Пошаговый мастер трансфера по зонам безопасности: **`ЗР ➔ ЗТ ➔ ЗПЭ`** (с проверкой SoD и цифровым конвертом).

## 3. Карточка Приложения (Application Detail) — Возвращение канона

Настройки и ЖЦ — это **не пункт главного меню**, а сердце карточки конкретного приложения (`/applications/:id`).

В карточке приложения восстанавливаются **6 канонических вкладок** из реверс-спеки `Карточка_Приложения_1_уровень.html`:

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 📱 Core Banking Gateway (Level 1 / ppod)                         [ ▶ Запустить сборку ]│
├──────────────┬────────────┬────────────┬───────────┬───────────────────┬───────────────┤
│ Информация   │  Сборки    │  Деплои    │  Релизы   │  Настройки & ЖЦ   │    Команда    │
│ (Overview)   │  (Builds)  │  (Deploys) │ (Releases)│    (Settings)     │    (Team)     │
└──────────────┴────────────┴────────────┴───────────┴───────────────────┴───────────────┘
```

### 3.1. Вкладка [1] «Информация» (Общие данные + Интеграции)
- **Общие данные (readonly):** Статус эксплуатации, дата создания, уникальный код (`slug`), тип приложения (Линкор/Крейсер/Модуль...), родительская группа L2, использование конфигураций, использование профилей, приоритет запуска (1–100).
- **Интеграции:** Статус привязки Git (Gitea/GitLab), CI-раннера (Woodpecker), трекера задач (JIRA), базы знаний (Confluence).
- **Контакты:** Ответственный IT-лидер, подразделение, телефон.

### 3.2. Вкладка [2] «Сборки» (Builds History — Первоклассная сущность)
- **Таблица сборок:**
  - ID сборки (UUID / short hash).
  - Название / Тег сборки.
  - Точный Git-коммит (SHA-256 / short SHA) и ветка.
  - Статус сборки: 🔵 `pending`, 🔵 `running`, 🟢 `success`, 🔴 `failed`, ⚪ `aborted`.
  - Время запуска и длительность.
  - Артефакты сборки (ссылки на MinIO / Nexus).
  - Инициатор (пользователь / webhook).
- **Действия:** «Создать сборку», «Остановить», «Развернуть», «Защитить от удаления».

### 3.3. Вкладка [3] «Деплои» (Deployments History — Первоклассная сущность)
- **Таблица развёртываний:**
  - ID деплоя.
  - Сегмент: `голый` / `интеграционный`.
  - Среда / Зона: `ЗР` (dev), `ЗТ` (test), `ЗПЭ` (prod).
  - Статус: 🔵 `pending`, 🔵 `running`, 🟢 `success`, 🔴 `failed`, ⚪ `deleted`.
  - Ссылка на сборку (Build ID).
  - Среда исполнения (Runtime: OpenShift, Deckhouse, k8s).
  - URL сервиса (Endpoint).
  - Canary-параметры (если применимо).
- **Действия:** «Перезапустить», «Остановить», «Откатить (Rollback)».

### 3.4. Вкладка [4] «Релизы» (Releases)
- Список релизных версий приложения (SemVer: v1.0.0, v1.0.1-hotfix).
- Тип релиза (Обычный, Hotfix, Квартальный).
- Статус допуска и текущая зона (`ЗР` / `ЗТ` / `ЗПЭ`).
- Кнопка «Трансфер в следующую зону».

### 3.5. Вкладка [5] «Настройки & Конфигурация ЖЦ» (Settings & LC)

## 4. Сквозной канонический конвейер (The Steel Thread Pipeline)

Каждая операция в системе обязана ложиться в непрерывный проверяемый граф:

```text
1. Application (Приложение L0/L1/L2) + Git RepositoryBinding
     │
     ▼
2. Settings & LC Configuration (14 шагов, флаги, условия продолжения)
     │
     ▼
3. Pipeline Plan (DAG компиляция шагов через PlanCompiler, compiled_hash)
     │
     ▼
4. Build (Сборка: точный commit SHA, сборщик Woodpecker, бинарные артефакты)
     │
     ▼
5. Run & Batches (Выполнение: BuildBatch → StaticScanBatch → DeployBatch → DynamicTestBatch)
     │
     ▼
6. Findings & Evidence Ledger (Нормализованные уязвимости, SHA-256 журнал, ГОСТ-Акт)
     │
     ▼
7. Security Gate (Автоматические пороги CVSS/CWE + Ручная подпись Admission Gate)
     │  [ SoD Enforcement: release.initiator_user_id != gate.decided_by ]
     ▼
8. Release (Релизный манифест, запечатанный из точного Build)
     │
     ▼
9. Release Transfer & Zone Promotion (Строго ЗР ➔ ЗТ ➔ ЗПЭ через Digital Envelope)
```

## 6. План санитарных работ (Implementation Slices)

После утверждения данной спецификации работы выполняются в 3 чистых шага:

### Шаг 1: Физическое удаление мусора из фронтенда
- Удалить файлы: `RbacConsole.tsx`, `SlaRemediationWidget.tsx`, `ExecutivePostureWidget.tsx`, `SbomExplorer.tsx`, `EmergencyDeck.tsx`, `SocRadar.tsx`, `ThreatModeler.tsx`, `BlastRadiusView.tsx`.
- Вычистить все импорты и 14 мертвых роутов из `ControlStationShell.tsx`.
- Сайдбар: строго 6 пунктов (`Overview`, `Applications`, `Pipelines`, `Runs`, `Gates`, `Releases`).

### Шаг 2: Реализация канонической Карточки Приложения
- Переписать `Applications.tsx`: при клике на приложение открывается `ApplicationDetail.tsx` с 6 вкладками (`Информация`, `Сборки`, `Деплои`, `Релизы`, `Настройки & ЖЦ`, `Команда`).
- Внедрить реальные `AppSettings.tsx` с 3 аккордеонами и 14 шагами ЖЦ.
- Удалить все клиентские `Math.random()` и mock-генераторы — при ошибке бэка честно показывать `<EmptyState />` или `<Alert severity="error" />`.

### Шаг 3: Серверное запечатывание безопасности (SoD + RBAC + Secrets)
- Завершить `[COS-031]` — честный `PrincipalContext` в `api/deps.py` без `return True`.
- Завершить `[COS-032]` — закрытие мутаций через `require_capability`.
- Завершить `[COS-033]` — выравнивание DTO `TransferRequest`.
- Завершить `[COS-034]` — серверный SoD (HTTP 409 при попытке автора подписать свой допуск).
- Завершить `[COS-035]` — валидатор `VaultSecretRef`.
- Завершить `[COS-037]` — полный сьют негативных тестов (401, 403, 404, 409).
