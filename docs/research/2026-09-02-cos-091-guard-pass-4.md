# COS-091 — Guard Pass 4: унификация in-body auth → deps-guards (releases/runs)

> Дата: 2026-09-02 · PO: Cosmo · Executor: Apex (worker-сессия)
> Статус: **закрыт** · Полный сет: **2312 passed / 2 skipped / 0 failed**
> Зависимости: COS-083 (резолв-контракт) ✅, COS-086 (guard pass 3) ✅

## 1. Что было

Скан, зафиксированный в COS-086, показал в releases.py/runs.py гибридный auth:
часть решений принималась deps-гвардами, часть — in-body, часть поверхности
была полностью анонимной.

| Поверхность | Состояние до COS-091 |
|---|---|
| `POST /releases/{id}/submit`, `/approve`, `/reject`, `/deploy`, `DELETE /releases/{id}` | **Полностью анонимные lifecycle-writes** |
| `POST /releases/envelope/verify` | Анонимная crypto-oracle |
| `create_release`, `create_run` | deps-guard + **in-body** сравнение `body.domain_id != principal.domain_id` (вне резолв-контракта) |
| `PATCH /runs/{id}/status` | Write с голым principal (гибрид, без capability) |
| `GET/POST /batches`, `GET/PATCH /batches/{id}/status` | **Полностью анонимная семья** (Batch без собственного domain_id) |

notifications.py (13 in-body `get_current_principal`) — зона Flash, есть её
WIP; **сознательно не тронут** (out of scope карточки, координация через PO).

## 2. Решение

### 2.1 releases.py

| Роут | Гвард после COS-091 |
|---|---|
| `POST ""` (create) | RELEASE_CREATE + in-body проверка заменена резолв-контрактом (`resolve_caller_domain`); сообщение 403 сохранено |
| `POST /{id}/submit` | `release:submit` (lead/relmgr, ЗР) + ghost-404 |
| `POST /{id}/approve` | `release:approve` (security officer — SoD) + ghost-404 |
| `POST /{id}/reject` | `release:reject` (security officer) + ghost-404 |
| `POST /{id}/deploy` | `release:deploy` (lead/relmgr, **ЗТ** — зонная матрица даёт 403 в ЗР) + ghost-404 |
| `DELETE /{id}` | `release:create` (владелец жизненного цикла; отдельного release:delete в матрице нет — rbac frozen не расширяли) + ghost-404 |
| `POST /envelope/verify` | `envelope:verify` (qa/relmgr/auditors); pure-функция, доменного якоря нет |
| transfer/transfer-v2 | Уже guarded (COS-083), не менялись |

Все Actions уже существовали в rbac.py — frozen-счётчики rbac-регресса
не тронуты.

### 2.2 runs.py

- `create_run`: in-body сравнение заменено на `resolve_caller_domain`
  (поведенческое отличие: не-админ с пустым identity может привязаться по
  заголовку — тот же контракт, что create_plan в COS-086).
- `PATCH /runs/{id}/status`: + `scan:start` (кто запускает прогоны, тот и
  ведёт статусы); ghost-404 сохранён.
- **Batches** (якорь `batch.plan_id → plan.app_id → Application.domain_id`,
  тот же паттерн, что list_plans):
  - `GET /batches`, `GET /batches/{id}` → require_principal + доменный
    scoping / ghost (helper `_batch_domain_map`);
  - `POST /batches`, `PATCH /batches/{id}/status` → `scan:start` + ghost.

### 2.3 Попутно закрытый латентный prod-баг

`approve/reject` писали `ReleaseApproval.model_dump()` (с `decided_at:
datetime`) напрямую в JSONB → asyncpy `TypeError: Object of type datetime is
not JSON serializable` на UPDATE. Путь был не покрыт API-тестами (e2e работают
с доменными объектами напрямую) — воспроизведён первым lifecycle-тестом.
Фикс: `model_dump(mode="json")`.

## 3. Тесты

`test_deps_guard_regression.py`:
- GUARDED_ROUTES +9 (anon 401 / USER 403 автоматически).
- GUARD_PASS_MATRIX +9 строк: batches (svc, 404/404), run status (svc, 404),
  submit (relmgr, 404), approve/reject (**secoff**, 404 — SoD-держатель),
  delete (relmgr, 404), envelope/verify (qa, 200 verified=false).

  (SECURITY_OFFICER).

  читает batches (200); happy path submit→approve сквозь гварды; SoD

  deploy — 403 в ЗР по зоне, ghost-404 в ЗТ; run status guard+ghost;
  batches scoping + ghost + create/PATCH/GET свой.

  dynamic_test}; в тестах используется `static_scan`.

  параметризация по `releases.py` и `runs.py` (pipelines.py сохранён
  отдельным тестом) — in-body auth в этих файлах не вернётся без падения CI.
