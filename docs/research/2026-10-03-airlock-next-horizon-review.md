# Airlock — следующий продуктовый горизонт

> **Дата:** 2026-10-03  
> **Владелец:** Cosmo  
> **Статус:** позиция для обсуждения, не канон и не разрешение на реализацию.  
> **Основание:** текущие локальные backlog/research и межпродуктовая roadmap.  
> **Граница:** этот документ не создаёт карточек, не назначает воркеров и не меняет чужие контракты.

## Короткий вывод

Дальше не стоит наращивать отдельные функции. Целевой результат Airlock — замкнуть
проверяемый инженерный цикл, в котором один авторизованный оператор работает с
точной ревизией, безопасно фиксирует изменение, получает отдельный исход запуска,
доказательства и решение Hub. До этого нужно закрыть текущую приёмку и согласовать
стыки identity/revision; уже реализованные поверхности повторно не строить.

Предлагаемая последовательность: освежить WIP → сверить существующий assurance spine
и межпродуктовые контракты → закрыть начатый source-SAST этап → доказать
авторизованное чтение workspace → доказать safe commit → связать commit → run →
evidence → новое решение Hub. Масштабирование и интерактивный PTY остаются поздними
направлениями.

## Позиция Airlock по трём вопросам roadmap

| Вопрос | Позиция | Причина и граница |
|---|---|---|
| Минимальная передача identity от Airlock к IDE | **needs-evidence** по конкретному handoff; **agree** по инвариантам | IDE должна обращаться от имени того же проверенного principal; URL не содержит credential, IDE не получает secret values и не становится отдельным identity-provider. API умеет принимать Bearer и session-cookie, однако просмотренный login-flow не доказывает выпуск браузерной cookie; текущая Control Station использует браузерный Bearer. Предпочтительный кандидат — Airlock-owned HttpOnly/Secure-сессия на согласованной same-site границе с защитой от CSRF. До заморозки нужны подтверждённые production-origin/deployment topology, logout/revocation, scope и негативные случаи. Не передавать токен через URL, fragment или postMessage. |
| Текущая ветка и immutable snapshot | **agree** с разделением | Текущая ветка — mutable workspace с CAS для записи; commit snapshot — immutable и read-only. Черновик другой ревизии не подмешивается в snapshot. Commit, run intent, run outcome, evidence и QG verdict — отдельные факты с корреляцией, не единый «успех». Межпродуктовая ссылка должна нести полный commit SHA: текущая серверная терпимость к короткому префиксу не должна становиться обещанием однозначной finding-ссылки. |
| Первый вертикальный результат Airlock | **agree**: авторизованное открытие точного workspace-контекста | Это минимальная проверка trust boundary и предпосылка записи; в текущем обзоре не доказано, что отдельная IDE получает рабочую сессию того же principal. Результат: оператор открывает нужные repo/branch/file в разрешённой ревизии, видит фактическую ревизию и получает честный отказ/empty-state вместо незаметного fallback. Затем — safe commit, затем полный commit → run → evidence. |

### Проверка assurance spine

Airlock уже имеет локальные Contract A/B/C поверхности и fail-closed transfer gate;
поэтому не предлагаем переписывать эту линию. Перед новым feature-пакетом Keeper и
Arbiter должны подтвердить, есть ли свежий representative evidence для пути
SecOps execution/evidence → Hub QG → Airlock transfer decision, включая отрицательный
случай. Если доказательство есть — сохранить его как основу. Если нет — согласовать
минимальный контрактный proof, не открывая новый широкий эпик.

## Рекомендуемый порядок

### 0. Закрыть фактический WIP и обновить картину

- Получить свежие отчёты по уже выданным COS-193 и PTY-SANDBOX-1.1; не считать их
  завершёнными только по старой записи.
- Для COS-193 подтвердить успешное чтение run detail и run list с findings и
  сохранение корректного содержимого.
- Для PTY-SANDBOX-1.1 подтвердить attach/workspace-delivery и негативы без ослабления
  изоляции. Это внутренний sandbox-шов, не разрешение начинать свободный shell.
- Одним preflight проверить, что восстановленный Docker/dev-профиль, frontend edge
  и registry действительно здоровы. COS-195 уже принят; при обнаружении нового
  дефекта сначала зарегистрировать факты, а не заводить карточку автоматически.
- До свежих отчётов, разрешения Максима и приёмки текущего WIP новые диспатчи не
  выпускать.

### 1. Согласовать доверенные межпродуктовые границы

- Собрать позицию Vector по session handoff и wire PTY; позицию Arbiter по finding
  occurrence, точной ревизии и новому QG-решению; подтверждение Keeper по producer
  facts, provenance и ошибочным/неполным результатам.
- Подтвердить актуальность уже принятых Contract A/B/C и representative
  assurance-spine evidence. Timeout, недоступность или неполное evidence остаются
  `UNKNOWN/BLOCKED`, никогда не PASS.
- Заморозить один контрактный ответ на identity и полный revision identity до
  межпродуктовой реализации. Не создавать Horizon-карточки до review Максима.

### 2. Закрыть начатую source-SAST Phase 1

SAST-GATE-3 — ближайший готовый пакет существующего трека после свежей приёмки
COS-193, уточнения gate-policy и разрешения на новые выдачи. Приёмка должна довести
реальный скан от отчёта до evidence/findings/gate/Hub, включая плановый rebuild runtime
и полный Woodpecker прогон, не дублируя container scans. COS-194 принята на уровне
кода/контракта; до обновления контейнера не считать live runtime исправленным.

Это ограниченный close-out уже начатого направления, а не смена стратегического
фокуса с инженерного цикла на расширение сканеров.

### 3. Первый новый пользовательский срез: authorized workspace read

**Ожидаемый результат:** из Airlock оператор открывает Web IDE на точных repo,
branch, file и revision; IDE обращается через Airlock от имени того же principal.
Доступ, неверная цель и отсутствующая ревизия видны честно; credential не попадает
в URL, а исторический snapshot не превращается в изменяемую ветку.

Переиспользовать уже принятые bootstrap, branch-CAS и read-only snapshot механики;
проверять интеграционный контракт с Vector, а не повторно реализовывать API.

### 4. Следом: safe commit

**Ожидаемый результат:** write возможен только в разрешённом mutable workspace;
перед записью проверяются актуальность ветки и файловой базы; конфликт typed и не
создаёт частичного/ложного commit; повтор после сетевой неопределённости имеет
однозначный результат; actor, revision и исход аудируемы. Immutable snapshot остаётся
только для чтения.

Уже реализованные CAS/409 и FE-поверхности сначала проверяются в целевом клиенте;
не объявлять кросс-продуктовое поведение готовым по одной лишь локальной приёмке.

### 5. Затем: commit → run → evidence → Hub decision

**Ожидаемый результат:** запуск явно привязан к созданному commit; принятие run intent
не выдаётся за завершённый run; логи восстанавливаются после reconnect; findings и
evidence имеют provenance к точному run/commit; Hub принимает новое решение, а
Airlock применяет его к lifecycle/transfer. Отсутствие отчёта, таймаут или отказ
остаются видимыми и fail-closed.

### 6. Позже: точные finding snapshots, затем эксплуатационное расширение

- После подтверждения полного commit identity связать eligible source-findings с
  immutable snapshot; artifact-only findings не получают искусственную IDE-ссылку.
- Продвигать масштабирование SAST, CodeScoring и дополнительные интеграции только
  при подтверждённом спросе и владельческом решении.
- Продолжать PTY SERVER/STREAM/HARDEN/FE только после согласования wire и при
  отдельном приоритете. PTY остаётся default-off, allowlist-scoped и изолированным;
  verified execution остаётся у обычного runner.

## Решения и риски перед следующим пакетом

1. **Identity handoff** не подтверждён end-to-end. Нужна совместная позиция Cosmo +
   Vector; нельзя объявлять готовность по факту поддержки cookie в API.
2. **Полный revision identity** должен совпадать у Hub, Airlock и IDE. Сокращённый
   SHA допустим только как локальная удобная форма, не как authority deep-link.
3. **Assurance spine** имеет уже реализованные контракты, но нужен свежий сквозной
   evidence и отрицательная приёмка до решения «уже доказано / требуется proof».
4. **WIP и git-состояние датированы:** текущие статусы воркеров требуют обновления;
   большой незафиксированный пласт нельзя коммитить без явной команды Максима.
5. **Source-SAST semantics:** действующий локальный план трактует scanner failure как
   terminate, findings — через severity policy, v1 — security-only. Это рабочая
   позиция Cosmo; отдельно подтверждать у Максима, если GATE-3 расширяет Quality/
   coverage или меняет политику.

## Не делать сейчас

- Не диспатчить новые задачи и не создавать дубли уже принятых workspace/SAST/transfer
  поверхностей.
- Не заменять Web IDE собственным identity-provider, не пускать её напрямую в Forge,
  Hub, runner или secret store.
- Не включать PTY по умолчанию, не запускать произвольный shell, не смешивать PTY с
  подтверждённым pipeline-run.
- Не оживлять SAST worker-pool и не начинать CodeScoring без доказанного масштаба или
  решения владельца.
- Не править головной MASTER за Vector; статус PK-C-010 передать на синхронизацию.
- Не коммитить и не push без явной команды Максима.
